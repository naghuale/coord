# План UX-1: что важно → что нужно → как сделаем → что будет

Статус: срез B реализован локально; срезы A и C и полный сценарный прогон открыты.
Документ отвечает на четыре вопроса и связывает их с нормативными материалами:
[ALIGNED_UX.md](ALIGNED_UX.md) (поведение и критерии), [UX_TASK.md](UX_TASK.md)
(задача на реализацию), выводы аудита F1–F4 в ../../UX_AUDIT.md.

---

## 1. Что важно (почему это первый приоритет)

Важно то, что блокирует доверие к системе как к продукту, а не только то,
что технически сломано:

1. **Честность статуса важнее красивого статуса (F1).** Первый живой обмен
   прошёл, но ATTACHED маскировал недоступность провайдера. Пока owner не
   может отличить «агент подключён» от «агент способен работать», любые
   назначения ролей делаются вслепую. Это фундамент: без него остальные
   улучшения интерфейса показывают неверные данные.
2. **Полномочия не должны меняться незаметно (F3 → fencing).** Длинный путь
   с флагами — неудобство; но опаснее потеря привязки профиля к поколению
   контекста: старый TUI после resume не должен получить новые полномочия.
   Поэтому удобство (профили) проектируется вместе с безопасностью, а не
   вместо неё.
3. **Onboarding без ручных подсказок (F2).** Если новому owner нужны заранее
   известные REF и сторонние инструкции, система не работает как продукт.
   Recovery-путь обязан пройти без вмешательства человека в середине.
4. **Неизвестное должно оставаться неизвестным.** Coord не всегда может сам
   узнать о лимите модели. Правильный ответ — `unknown` + явный сигнал от
   owner/интеграции, а не догадка. Это принцип, ограничивающий объём
   реализации: мы не строим детектор квот.
5. **Проверенное ≠ подтверждённое.** Восстановление LongCat не проверено из-за
   подтверждённого лимита провайдера — оно вынесено из приёмки первого
   этапа, чтобы дефект интерфейса не приняли за дефект восстановления.

Что сознательно НЕ важно на этом этапе: новые свойства протокола, delivery
семантика (доставка ≠ принятие), многопользовательский доступ, UI-красота
сверх читаемости карточки.

## 2. Что нужно (минимальный набор требований)

Ровно три артефакта реализации + один прогон:

- **N1. Профиль контекста** (`--profile`): хранит state path daemon'а,
  session ID, context ID, pointer на credential-file, generation. Файл 0600
  под XDG. Секрет не копируется. Обязателен структурированный отказ stale-
  профилю после resume (generation изменился) с подсказкой refresh. Запрещён
  auto-select newest credential. Durable operation ID сохраняется клиентом
  до отправки (идемпотентность повторов).
- **N2. Карточка состояния комнаты**: раздельные поля attachment / transport
  reachability / readiness / processing cursor / last activity / provider
  availability / blocker / ожидание. Ни одно поле не выводится из другого.
  Блокер `blocked_provider_quota` — машинное состояние
  (reason/source/observed_at/retry_at): останавливает новые назначения
  ролей, не трогает checkpoint/journal.
- **N3. Честный discovery/onboarding**: discover показывает найденные агенты
  с refs и временем наблюдения; приглашённый агент получает уведомление invite
  и команду attach, создающую профиль; пустой wait по таймауту — штатное
  состояние, не ошибка.
- **N4. Прогон сценария «от начала до восстановления»** (15 шагов из
  ALIGNED_UX.md §4) двумя TUI на fake clock/transport сначала, затем live —
  участники Codex Auditor и Nemotron; LongCat вне приёмки до снятия квоты.

Ничего сверх N1–N4 в задачу не входит.

## 3. Как сделаем (порядок и метод)

Три горизонтальных среза, каждый тестами до live-прогона; порядок выбран так,
чтобы безопасность проверялась раньше удобства:

1. **Срез B первым (карточка + блокеры).** Он ничего не ломает в API, даёт
   наблюдаемость сразу, и именно через него потом проверяются эффекты
   среза A (stale-профиль виден как отдельное состояние, а не как ATTACHED).
   Тесты: таблица переходов полей, fake «нет ответа транспорта», fake
   «owner сообщил о квоте».
2. **Срез A вторым (профили).** Строится поверх уже честных состояний.
   Ключевой тест — fencing: создать профиль, SIGKILL daemon, resume
   (generation↑), попытка работы со старым профилем → структурированная
   stale-ошибка, новых полномочий нет; refresh → работа продолжается.
   Обратная совместимость: все старые длинные флаги проходят те же тесты
   без изменений.
3. **Срез C третьим (discovery/onboarding).** Собирает A+B в путь нового
   owner: init → start --coordinator → discover → invite → attach → ready →
   say/wait/checkpoint/ack.
4. **Интеграционный прогон (N4)** — полный сценарий, включая перезапуск
   daemon'а и восстановление обеих сессий без ручных подсказок в середине.
5. Границы, которые не трогаем: protocol/fencing семантика (только additive
   статусные поля), поведение daemon при потере связи, quota-детекция внутри
   Coord (её нет и не будет — только приём внешнего сигнала).
6. Оформление: каждый срез — отдельный коммит с тестами; PR только после
   зелёного fake-прогона; live-прогон фиксируется в CHANGELOG ссылкой на
   seq-события.

## 4. Что будет (измеримый результат)

После принятия UX-1:

- **Owner:** одной командой видит комнату, где «подключён», «готов»,
  «обработано до seq», «последняя активность», «доступность провайдера
  (в т.ч. unknown)» и «кого/чего/до когда ждём» — раздельно и без домыслов;
  при `blocked_provider_quota` новые назначения не выдаются, journal цел.
- **Агент:** узнаёт о приглашении сам, подключается одной командой attach,
  дальше работает короткими командами `--profile …` без абсолютных путей.
- **Безопасность:** старый TUI после resume гарантированно получает stale-
  ошибку, а не новые полномочия; повтор lost-response идемпотентен.
- **Приёмка:** 9 критериев из ALIGNED_UX.md зелёные на fake-транспорте;
  live-прогон двух TUI проходит путь «приглашение → обмен → kill daemon →
  восстановление обеих сессий» без ручных подсказок. Единственная известная
  незакрытая ветка — LongCat-recovery, явно помеченная как заблокированная
  подтверждённой квотой провайдера (F4), с планом перепроверки после её
  снятия.
- **Что это открывает:** следующий кандидат в бэклог — снятие F4-проверки
  (LongCat recovery) как отдельный live-тест, и лишь затем — расширение
  круга ролей/комнат.
