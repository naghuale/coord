## 2. Порядок работ (решено OWNER, R69)

Противоречие, найденное при написании проекта: ROADMAP относил
«owner/agent command boundary» к ADR-0006 и ставил ADR-0006 после P0-3, хотя
P0-3 сам реализует production write path через эту границу — разрыв «проект до
кода». OWNER выбрал вариант A (R69). ROADMAP исправлен его владельцем (Codex):
до P0-3 обязательны принятый проект границы команд Owner (этот документ) и
отдельный проект границы команд агентов; ADR-0006 оставлен для read API и
projections без авторизации записи. Точный список зависимостей — §5.

Рассмотренные варианты (для истории решения):

- **A.** P0-2 завершается как основа хранилища: каноническое состояние, модель
  и внутренний API под тестами, без внешних команд изменения Task. Принятый
  проект границы (этот документ или его часть в ADR-0006) становится
  обязательной зависимостью P0-3: P0-3 заблокирован до его приёмки. В ROADMAP
  граница вносится в зависимости P0-3; остальной ADR-0006 (read API,
  projections, Startup Card) остаётся на прежнем месте.
- **B.** В P0-2 входит узкая граница: только Owner, только команды над своей
  Task, локальный транспорт. P0-3 расширяет её на агентов и CLI. ROADMAP и
  DESIGN синхронизируются.

Рекомендация: **A**. Причина — пункт 3.1: без решения о том, что отличает
человека от агента, граница из варианта B даёт не доказанный TM-05, а ещё один
секрет, доступный агентам. Вариант B оправдан, только если OWNER выберет
механизм из 3.1, недоступный агентским процессам.

Следствие R69: поручение R67 закрывается как проект, а не как срез кода P0-2.
P0-2 — только основа хранилища; реализация границы начинается в P0-3 после
приёмки этого проекта.

## 3. Предлагаемая модель

### 3.1. Owner principal (решает OWNER)

TM-05 требует стабильного человеческого principal, отличного от `agent_id`.
Агенты работают под тем же OS user, что и человек, поэтому любой файл, который
может прочитать CLI человека, может прочитать и агент. Отсюда варианты:

1. **Ключ в том же OS user** (как `owner.key`). Просто, но не отличает человека
   от агента. TM-05 не доказывается; это нужно прямо записать как допущение.
2. **Подтверждение вне агентского канала.** Daemon выдаёт одноразовый код;
   человек подтверждает его через устройство или окно, к которому у агента нет
   доступа (например, OS keychain с запросом подтверждения). Отличает человека,
   но требует интерактива и выбора платформенного механизма.
3. **Отдельный OS user для агентов.** Ключ owner недоступен агентам по правам
   файловой системы. Самая сильная граница, но меняет эксплуатацию всех сессий.

По R70 для P0-3 выбран вариант 2, вариант 3 — цель P0-5. Ни консоль, ни
локальный вход под тем же OS user не считаются подтверждением вне агентского
канала: агент может прочитать тот же файл и запустить ту же команду CLI.

#### 3.1.1. Механизм подтверждения (выносится OWNER)

Ключевое ограничение: всё, что хранит daemon, лежит под тем же OS user и
доступно агентам. Поэтому daemon может хранить только данные для проверки, но
не секрет, которым подтверждение создаётся.

Критерии сравнения (R70): macOS; Linux; устойчивость к агенту под тем же OS
user; интеграция с daemon.

| Механизм | macOS | Linux | Устойчивость к агенту | Интеграция с daemon |
|---|---|---|---|---|
| Аппаратный ключ FIDO2 / WebAuthn | Да | Да | Высокая: daemon хранит только открытый ключ, подпись требует касания | Локально, без сети; challenge привязывается к команде |
| Системная связка ключей с подтверждением (macOS LocalAuthentication) | Да | Нет единого механизма | Высокая на macOS: подтверждение Touch ID или паролем в системном окне | Нужен cgo и Security framework; на Linux нет замены |
| Подтверждение на отдельном устройстве (подпись ключом устройства) | Да | Да | Высокая, если daemon хранит только открытый ключ устройства | Нужен канал до устройства; локальный режим требует сопряжения |
| MFA push через внешнего провайдера | Да | Да | Зависит от провайдера; API-ключ провайдера в daemon доступен агенту, и агент может сам запросить push. Человек видит запрос, но может подтвердить его по ошибке | Нужны сеть и внешний сервис; появляется внешняя зависимость отказа |
| TOTP (для сравнения, недопустим) | Да | Да | Нет: daemon хранит общий секрет, агент читает его и вычисляет код | — |

Во всех вариантах запрос на подтверждение должен показывать человеку саму
команду (TaskID, действие, ожидаемую Revision). Иначе агент может запустить
своё подтверждение в момент, когда человек ждёт своего.

Рекомендация: FIDO2, причём подтверждение на каждую команду изменения Task.
Единственный вариант, одинаково работающий на macOS и Linux без сети и без
секрета в хранилище daemon. Связка ключей macOS — допустимая дополнительная
реализация того же интерфейса подтверждения.

Challenge — это не просто «хеш команды». Daemon выдаёт его на конкретную
команду, и он содержит:

- идентификатор команды (message ID для Inbox receipt);
- TaskID, действие и хеш канонически сериализованных входных данных;
- ожидаемую Revision и generation сессии;
- одноразовый nonce и срок действия.

Daemon помечает nonce использованным в том же durable commit, что и команду.
Неиспользованные nonce после перезапуска daemon недействительны (fail-closed).
Подтверждение с истёкшим, повторным или выданным на другую команду nonce
отвергается.

Доверенный показ. Authenticator FIDO2 подтверждает присутствие, но не
показывает, что подписывается. Перед касанием CLI Owner показывает Task,
действие, входные данные, их эффект и ожидаемую Revision, разобранные из тех же
байтов challenge, которые уходят на подпись. Остаточный риск: под тем же OS
user агент может запустить свой процесс с поддельным показом и запросить
касание. Правило эксплуатации: касаться только в ответ на собственную команду.
Полностью риск снимает только отдельная OS identity агентов (P0-5); это
ограничение записывается в OPERATIONS вместе с реализацией.

Подтверждение нельзя повторно использовать для другой команды: оно годно
только для того challenge, на который выдано.

Почему подтверждение на каждую команду, а не на сессию: выданную capability
процесс CLI держит в памяти, а на Linux при `ptrace_scope = 0` процесс того же
OS user может её прочитать. Подтверждение одной конкретной команды этой утечке
не подвержено.

Не проверено (UNKNOWN): какая Go-библиотека или внешняя утилита FIDO2 будет
использоваться и её реальный API. Выбор делается при реализации P0-3 по
реальной документации; вымышленные вызовы SDK не допускаются.

Без решения OWNER по 3.1.1 остальные пункты проектируются, но не реализуются.

### 3.2. Сессия аутентификации Owner и generation

У Owner нет агентского Run и runtime Session (ADR-0001:577: Owner decision
проходит через Task-scoped capability без агентского Run). Поэтому здесь речь
идёт об отдельной сущности — сессии аутентификации, а не о runtime `Session`.

- `OwnerAuthSession{PrincipalID, Generation}`: отдельный агрегат канонического
  состояния, не часть Task и не часть runtime Session. Его изменения
  (открытие сессии, повышение generation, отзыв capability) — команды daemon с
  собственным DomainEvent и одним durable commit по RT-04.
- Команда Task читает `OwnerAuthSession` под той же сериализованной границей,
  что и Task; отзыв, закоммиченный раньше, гарантированно виден команде,
  обработанной позже.

**Открытый контракт (блокирует приёмку проекта).** Текущий канонический
`DomainEvent` относится к Task: TaskID обязателен, EventSeq и TaskRevision
принадлежат Task. `ApplyInboxCommand` тоже требует TaskID и Revision Task.
Значит, открытие сессии и отзыв capability в текущей модели можно записать
только через фиктивную Task, а это недопустимо. Нужно выбрать одно из двух:

- отдельный поток событий аутентификации со своей последовательностью и
  своим Inbox receipt;
- обобщённый конверт события и receipt команды, в котором Task — лишь один
  из видов агрегата.

Оба варианта меняют схему канонического состояния и ADR-0001/TASK-MODEL. Это
решение принимается отдельно, до приёмки проекта.

При любом варианте изменение `OwnerAuthSession`, его событие и receipt команды
фиксируются одним durable commit. `ApplyInboxCommand` остаётся границей только
для команд Task; если его расширяют на другие агрегаты, это отдельное явное
изменение с собственными тестами, а не молчаливое обобщение.
- Открытие новой сессии повышает `Generation` монотонно; все capability старых
  generation перестают действовать без отдельного отзыва.
- Хранение в каноническом состоянии меняет схему. `CanonicalSchemaVersion = 1`
  ещё не закоммичен, поэтому поле добавляется в версию 1 до первого коммита
  canonical.json, либо отдельным переходом схемы по ST-05. Владелец
  `store/canonical.go` — Codex; изменение согласуется с ним.

### 3.3. Capability

- Непрозрачный токен; daemon хранит только его хеш вместе с
  `{PrincipalID, Generation, TaskID, Actions}`.
- Scope — одна TaskID и явный список действий. Capability на создание Task —
  отдельное действие без TaskID.
- Отзыв: повышение generation или удаление записи; оба — durable commit.

### 3.4. Порядок проверки команды

Все проверки выполняются в daemon до вызова Task service, под той же
сериализованной границей, что и `ApplyInboxCommand`:

1. Аутентификация запроса → principal.
2. `Generation` из capability равен текущей generation principal.
3. TaskID и действие команды входят в scope capability.
4. `Task.OwnerID == PrincipalID`; при создании `OwnerID` берётся из principal, а
   не из тела запроса.
5. Ожидаемая `Revision` из запроса равна `Task.Revision` (TM-06).
6. `Task.Fence` и допустимость перехода (RT-06, TASK-MODEL).
7. Переход, DomainEvent, Inbox receipt и Outbox — один durable commit (RT-04).

Каждый отказ имеет свой код ошибки. Отказ ничего не пишет, кроме
диагностической метрики.

## 4. Тесты и мутации

На каждый пункт из 3.4 — отрицательный тест, в котором нарушено ровно это
условие, а все остальные выполнены. Тест проверяет конкретный код отказа, а
также то, что состояние и Revision не изменились.

| Условие | Тест (целевой) | Мутация, которую тест обязан убить |
|---|---|---|
| 1 | TestTaskCommandRejectsUnauthenticated | проверка аутентификации отключена |
| 2 | TestTaskCommandRejectsStaleGeneration | сравнение generation отключено |
| 3 | TestTaskCommandRejectsCapabilityForOtherTask | проверка TaskID в scope отключена |
| 3 | TestTaskCommandRejectsActionOutsideScope | проверка действия отключена |
| 4 | TestTaskCommandIgnoresOwnerIDFromBody | OwnerID берётся из тела запроса |
| 4 | TestTaskCommandRejectsNonOwnerPrincipal | сравнение OwnerID отключено |
| 5 | TestTaskCommandRejectsStaleRevision | сравнение Revision отключено |
| порядок | TestTaskCommandChecksAuthorizationBeforeRevision | шаги 2–4 перенесены после 5 |
| 7 | TestTaskCommandCommitsEventReceiptAtomically | событие пишется вторым commit |

Тесты используют fake clock и fake transport. Существующий control token и
legacy SessionAuth не принимаются как замена ни в одном тесте.

## 5. Вне этого документа

Разделение с ADR-0006. Этот проект — зависимость P0-3 только для команд Owner
над Task. P0-3 по ROADMAP включает и запись агентов через Telepathy, поэтому
до начала P0-3 нужен ещё отдельный принятый проект границы команд агентов
(capability Run, Attempt, Task.Fence). В ADR-0006 остаются только read API,
projections, Startup Card и версионирование контракта.

Точные зависимости P0-3:

1. Принят `docs/plans/p0-2-task/COMMAND-BOUNDARY.md` (Codex и OWNER).
2. Принят проект границы команд агентов (файл ещё не создан; имя и владелец
   назначаются координатором).
3. Принято решение об открытом контракте из §3.2.

Критерий: P0-3 не начинается, пока в ROADMAP у P0-3 не стоят эти три
зависимости со ссылками на принятые документы. Зависимости 1 и 2 внесены в
ROADMAP его владельцем (Codex) 2026-10-08; после приёмки документов в ROADMAP
ставятся ссылки на принятые версии.

- Команды агентов и capability агентских Run — отдельный проект до P0-3.
- Read API и Startup Card (ADR-0006, ADR-0007).
- Отдельный OS user для агентов (P0-5, R70).
- Свободный текст в событиях (DESIGN.md §1, пункт 4).
- Удалённый, не локальный транспорт.
