## 3. Предлагаемая модель

### 3.1. Owner principal (решает OWNER)

TM-05 требует стабильного человеческого principal, отличного от `agent_id`.
Агенты работают под тем же OS user, что и человек, поэтому любой файл, который
может прочитать CLI человека, может прочитать и агент. Отсюда варианты:

1. **Ключ в том же OS user** (как `owner.key`). Просто, но не отличает человека
   от агента. TM-05 не доказывается; это нужно прямо записать как допущение.
2. **Подтверждение вне агентского канала.** Daemon выдаёт одноразовый код;
   человек подтверждает его через устройство или окно, к которому у агента нет
   доступа (например, OS keychain с запросом подтверждения). Отличает человека,
   но требует интерактива и выбора платформенного механизма.
3. **Отдельный OS user для агентов.** Ключ owner недоступен агентам по правам
   файловой системы. Самая сильная граница, но меняет эксплуатацию всех сессий.

По R70 для P0-3 выбран вариант 2, вариант 3 — цель P0-5. Ни консоль, ни
локальный вход под тем же OS user не считаются подтверждением вне агентского
канала: агент может прочитать тот же файл и запустить ту же команду CLI.

#### 3.1.1. Механизм подтверждения (выносится OWNER)

Ключевое ограничение: всё, что хранит daemon, лежит под тем же OS user и
доступно агентам. Поэтому daemon может хранить только данные для проверки, но
не секрет, которым подтверждение создаётся.

Критерии сравнения (R70): macOS; Linux; устойчивость к агенту под тем же OS
user; интеграция с daemon.

| Механизм | macOS | Linux | Устойчивость к агенту | Интеграция с daemon |
|---|---|---|---|---|
| Аппаратный ключ FIDO2 / WebAuthn | Да | Да | Высокая: daemon хранит только открытый ключ, подпись требует касания | Локально, без сети; challenge привязывается к команде |
| Системная связка ключей с подтверждением (macOS LocalAuthentication) | Да | Нет единого механизма | Высокая на macOS: подтверждение Touch ID или паролем в системном окне | Нужен cgo и Security framework; на Linux нет замены |
| Подтверждение на отдельном устройстве (подпись ключом устройства) | Да | Да | Высокая, если daemon хранит только открытый ключ устройства | Нужен канал до устройства; локальный режим требует сопряжения |
| MFA push через внешнего провайдера (допустим с остаточным риском, R106) | Да | Да | Ниже, чем у FIDO2: API-ключ провайдера в daemon доступен агенту, и агент может сам запросить push. Человек видит запрос, но может подтвердить его по ошибке; риск остаётся на стороне пользователя | Нужны сеть и внешний сервис; появляется внешняя зависимость отказа |
| TOTP (для сравнения, недопустим) | Да | Да | Нет: daemon хранит общий секрет, агент читает его и вычисляет код | — |

Во всех вариантах запрос на подтверждение должен показывать человеку саму
команду (TaskID, действие, ожидаемую Revision). Иначе агент может запустить
своё подтверждение в момент, когда человек ждёт своего.

Рекомендация: FIDO2, причём подтверждение на каждую команду изменения Task.
Единственный вариант, одинаково работающий на macOS и Linux без сети и без
секрета в хранилище daemon. Связка ключей macOS — допустимая дополнительная
реализация того же интерфейса подтверждения.

Challenge — это не просто «хеш команды». Daemon выдаёт его на конкретную
команду, и он содержит:

- идентификатор команды (message ID для Inbox receipt);
- TaskID, действие и хеш канонически сериализованных входных данных;
- ожидаемую Revision Task и ревизию набора credential principal (§3.2);
- одноразовый nonce и срок действия.

Для создания Task TaskID и Revision ещё нет. Challenge создания содержит вместо
них: действие `create`, PrincipalID (будущий `OwnerID`), хеш канонически
сериализованных параметров создания и ревизию набора credential. TaskID назначает
daemon после проверки подтверждения, в том же durable commit; подтверждение
поэтому привязано к параметрам, а не к TaskID. Повтор той же команды отсекается
по message ID и nonce, а не по ожидаемой Revision.

Daemon помечает nonce использованным в том же durable commit, что и команду.
Неиспользованные nonce после перезапуска daemon недействительны (fail-closed).
Подтверждение с истёкшим, повторным или выданным на другую команду nonce
отвергается.

Доверенный показ. Authenticator FIDO2 подтверждает присутствие, но не
показывает, что подписывается. Перед касанием CLI Owner показывает Task,
действие, входные данные, их эффект и ожидаемую Revision, разобранные из тех же
байтов challenge, которые уходят на подпись. Остаточный риск: под тем же OS
user агент может запустить свой процесс с поддельным показом и запросить
касание. Правило эксплуатации: касаться только в ответ на собственную команду.
Полностью риск снимает только отдельная OS identity агентов (P0-5); это
ограничение записывается в OPERATIONS вместе с реализацией.

Подтверждение нельзя повторно использовать для другой команды: оно годно
только для того challenge, на который выдано.

Почему подтверждение на каждую команду, а не на сессию: выданную capability
процесс CLI держит в памяти, а на Linux при `ptrace_scope = 0` процесс того же
OS user может её прочитать. Подтверждение одной конкретной команды этой утечке
не подвержено.

Не проверено (UNKNOWN): какая Go-библиотека или внешняя утилита FIDO2 будет
использоваться и её реальный API. Выбор делается при реализации P0-3 по
реальной документации; вымышленные вызовы SDK не допускаются.

Механизм выбран решением R109. Варианты, из которых шёл выбор, — §6.1.

### 3.2. Агрегат OwnerCredential (R110, R111)

У Owner нет агентского Run и runtime Session (ADR-0001, «Порядок реализации»:
Owner decision проходит без агентского Run; CM-12). При подтверждении каждой
команды (R109) сессия аутентификации, generation сессии и токен capability не
нужны: подлинность каждой команды доказывает подпись её challenge. Task-scoped
capability ADR-0001 (CM-12) в этой модели — подписанный challenge, привязанный к
одной команде одной Task: одноразовая форма capability, а не долгоживущий токен.

- `OwnerCredential` — отдельный агрегат канонического состояния, не часть Task
  и не часть runtime Session. Он хранит для principal набор credential: для
  каждого — идентификатор, открытый ключ, отпечаток, время регистрации и
  признак отзыва. Секретов в нём нет.
- `CredentialRevision` — монотонная ревизия набора credential principal.
  Регистрация и отзыв повышают её. Она играет роль generation: challenge,
  выданный при прежней ревизии, после отзыва недействителен.
- Изменения агрегата — команды `register` и `revoke` — пишутся в собственный
  поток событий со своей последовательностью и своим Inbox receipt. Изменение,
  событие и receipt фиксируются одним durable commit (RT-04). Фиктивная Task
  для этого не используется.
- `ApplyInboxCommand` остаётся границей только команд Task. Для
  `OwnerCredential` вводится отдельная граница команд с собственными тестами;
  молчаливое обобщение `ApplyInboxCommand` на другие агрегаты не допускается.
- Команда Task читает `OwnerCredential` под той же сериализованной границей,
  что и Task. Отзыв, закоммиченный раньше, гарантированно виден команде,
  обработанной позже.
- Схема: v1 расширяется до первой production-записи по образцу R85 (R110).
  Владелец `store/canonical.go` — Codex; изменение согласуется с ним.
- ADR-0001 перечисляет целевые канонические сущности (ADR-0001, «Целевые
  канонические сущности»); `OwnerCredential` добавляется туда явной правкой со
  ссылкой на R110 до начала реализации.

Регистрация (R111):

- Первые credential регистрирует человек отдельной командой инициализации
  канонического state; сейчас такой команды нет, она появляется в P0-3. По
  R113 команда регистрирует минимум два credential (основной и резервный) в
  одном durable commit и отказывает, если передан один. CLI показывает
  отпечаток каждого. Команда отказывает, если у principal уже есть хотя бы
  один credential, в том числе отозванный.
- Каждая следующая регистрация и каждый отзыв — подписанная команда с
  challenge, как команда Task (§3.3), подписанная действующим credential того
  же principal.
- Отзыв последнего действующего credential отклоняется (R113): иначе
  principal остаётся без способа подписать следующую команду, а повторная
  первая регистрация запрещена. Скомпрометированный ключ отзывается командой,
  подписанной другим действующим ключом. Потеря всех ключей — блокировка;
  выход только через новую инициализацию state.
- Остаточный риск TOFU: агент под тем же OS user может зарегистрировать
  программный authenticator раньше человека. Риск и правило эксплуатации
  (сверить отпечаток с ключом в руках) записываются в OPERATIONS вместе с
  реализацией.

### 3.3. Challenge и подписанная команда

- Challenge выдаётся daemon на одну конкретную команду (§3.1.1) и хранится
  только в памяти daemon до использования или истечения срока.
- Подписанная команда несёт challenge ID, подпись, идентификатор credential и
  те же байты команды, из которых строился challenge.
- Nonce помечается использованным в Inbox receipt той же команды: для команд
  Task — внутри `ApplyInboxCommand`, для `register` и `revoke` — в receipt
  потока `OwnerCredential`.

### 3.4. Порядок проверки команды

Все проверки выполняются в daemon до вызова Task service, под той же
сериализованной границей, что и `ApplyInboxCommand`. Control token проверяется
раньше как пропуск в канал (R112), но шагом авторизации не является.

1. Challenge с указанным ID выдан этим процессом daemon, срок не истёк, nonce
   не использован.
2. Подпись верна для открытого ключа указанного credential; credential
   принадлежит principal из challenge и не отозван.
3. `CredentialRevision` из challenge равна текущей ревизии principal.
4. Message ID, TaskID, действие, хеш входных данных и ожидаемая Revision в
   запросе совпадают с теми, что связаны в challenge. Для создания —
   message ID, действие `create`, PrincipalID и хеш параметров. Уникальный, но
   другой message ID или другие параметры — отказ.
5. `Task.OwnerID == PrincipalID`; при создании `OwnerID` берётся из principal,
   а не из тела запроса.
6. Ожидаемая `Revision` из запроса равна `Task.Revision` (TM-06). При создании
   этого шага нет; повтор отсекается шагом 1 и message ID.
7. `Task.Fence` и допустимость перехода (RT-06, TASK-MODEL). При создании
   Fence равен 0 (R94).
8. Переход, DomainEvent, Inbox receipt с использованным nonce и Outbox — один
   durable commit (RT-04).

Для `register` и `revoke` применяются шаги 1–4 и 8 к потоку
`OwnerCredential`; вместо шагов 5–7 — правила регистрации из §3.2.

Шаги 1–8 выполняются под одной сериализованной блокировкой команд. Проверить
подпись и ревизию credential вне блокировки, а затем отдельно вызвать
`ApplyInboxCommand`, нельзя: отзыв, закоммиченный между этими вызовами,
останется невидимым для команды.

Каждый отказ имеет свой код ошибки. Отказ ничего не пишет, кроме
диагностической метрики.

## 6. Вопросы на решение OWNER

§6.1–6.3 решены 2026-10-08 и сохранены как история выбора. OWNER принял
рекомендации: §6.1 — R109, §6.2 — R110 (модель) и R111 (первый credential),
§6.3 — R112, §6.4 — R113.

### 6.1. Механизм подтверждения (§3.1.1)

- **A (рекомендация).** FIDO2/WebAuthn, подтверждение каждой команды изменения
  Task. Daemon хранит только открытый ключ зарегистрированного credential.
- **B.** A плюс связка ключей macOS (LocalAuthentication) как вторая реализация
  того же интерфейса. Только macOS, требует cgo.
- **C.** MFA push через внешнего провайдера. Допустим по R106 с остаточным
  риском: агент может сам инициировать запрос.

Библиотека FIDO2 остаётся UNKNOWN до начала реализации P0-3 (§3.1.1).

### 6.2. Модель состояния аутентификации (§3.2)

Факт: `DomainEvent` и `ApplyInboxCommand` требуют TaskID
(`task/event.go:22`, сигнатура `ApplyInboxCommand` в `store/canonical.go`).

Следствие варианта 6.1 A: если подтверждается каждая команда, токен
capability и generation сессии из §3.2–3.3 не нужны. Проверка сводится к
подписи challenge зарегистрированным credential principal. Nonce помечается
использованным в receipt той же команды Task, то есть внутри
`ApplyInboxCommand`. Вне Task остаются только регистрация и отзыв credential.

- **A (рекомендация).** Отдельный агрегат `OwnerCredential`: свой поток событий
  (регистрация, отзыв) со своей последовательностью и своим Inbox receipt.
  Схема v1 расширяется по образцу R85, как для R108. Этой сущности нет в
  списке целевых канонических сущностей ADR-0001, поэтому ADR-0001 правится
  явно со ссылкой на решение. Роль generation играет
  ревизия набора credential: отзыв делает недействительными все challenge,
  выданные до него. §3.2–3.3 переписываются под эту модель.
- **B.** Обобщённый конверт события и receipt для любых агрегатов. Меняет
  модель DomainEvent в ADR-0001 и TASK-MODEL для всех агрегатов; объём
  больше, чем нужно для P0-3.
- **C.** Сохранить `OwnerAuthSession` и capability из §3.2–3.3 (нужно, если
  выбран механизм с подтверждением на сессию, а не на команду).

Вместе с моделью нужно решить регистрацию первого credential. Пока
credential нет, подписать регистрацию нечем; агент под тем же OS user может
зарегистрировать программный authenticator раньше человека. Варианты:

- **R-a (рекомендация).** Первую регистрацию выполняет человек при
  инициализации state (trust on first use). CLI показывает отпечаток
  credential. Каждая следующая регистрация и каждый отзыв подписываются уже
  зарегистрированным credential. Риск подмены при первой регистрации
  записывается в OPERATIONS.
- **R-b.** Принимать только credential с аттестацией производителя
  аппаратного ключа. Нужны корневые сертификаты производителей и их
  обновление; API библиотеки — UNKNOWN.

Остаточный риск при любом варианте: процесс под тем же OS user может
изменить файлы состояния напрямую, минуя daemon, в том числе набор
credential. Граница защищает канал команд, а не файлы. Полную защиту даёт
только отдельная OS identity агентов (P0-5, R70).

### 6.3. Транспорт команд Owner

Факт: daemon уже слушает control API по HTTP на numeric loopback TCP со
статическим токеном (`daemon/daemon.go:60`, `internal/coorddconfig/config.go:88`,
`control.go:22`).

Подлинность команды доказывает подпись challenge (§3.1.1), а не канал.
Доставка по транспорту не считается подтверждением.

- **A (рекомендация).** Отдельные пути на существующем control listener:
  выдача challenge и подписанная команда. Control token остаётся пропуском в
  канал (в том числе от запросов из браузера на loopback), но авторизацией не
  считается. Новых listener нет.
- **B.** Отдельный Unix socket 0600 в state. Недоступен другим OS user и
  браузеру без токена, но это второй listener со своим жизненным циклом. От
  агента под тем же OS user защищает не лучше варианта A.
- **C.** Через Telepathy. Не рекомендуется: это агентский канал, R70 требует
  подтверждения вне него.

### 6.4. Потеря или компрометация последнего credential (решено R113)

Вопрос поднят при ревью R110–R111. По §3.2 первый credential регистрируется
один раз, а последний действующий отозвать нельзя. Если этот ключ потерян или
скомпрометирован, Owner не может подписать ни одной команды, а
скомпрометированный ключ нельзя отозвать. Способа восстановления нет.

- **A (рекомендация).** При инициализации регистрируются минимум два
  credential: основной и резервный ключ, хранимый отдельно. Отзыв последнего
  действующего credential по-прежнему отклоняется. Потеря обоих ключей —
  блокировка; выход только через новую инициализацию state. Это правило
  записывается в OPERATIONS.
- **B.** Как A, плюс офлайн-перерегистрация: при остановленном daemon человек
  выполняет отдельную команду, которая отзывает все credential и регистрирует
  новый с записью события в истории `OwnerCredential`. Защищает не больше, чем
  TOFU: агент под тем же OS user может выполнить ту же команду. Остаточный
  риск тот же, что у прямой правки файлов (§6.2).
- **C.** Принять блокировку как политику: один credential, восстановления нет,
  кроме новой инициализации state.
