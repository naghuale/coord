# ADR-0003: External Reference Model

- **Статус:** Accepted
- **Дата:** 2026-10-07
- **Редакционная пометка:** 2026-10-10: добавлен PriorStatus в структуру, EXT-11 command boundary, provider evidence требования, явный порядок replay/revision, ограничения Metadata, маркер API как будущего контракта; исправлена разрядность entropy с 128 на 80 бит; унифицирован OWNER; уточнена неизменяемость identity в EXTERNAL_REFERENCE_UPDATED — FD, без изменения принятых инвариантов
- **Область:** каноническая идентичность Task и ссылки на внешние системы
- **Связанные решения:** ADR-0001 Canonical Coordination Model; ADR-0002 Project Dependency Graph

## Назначение

Coord владеет канонической идентичностью Task, workflow, Runs, событиями,
Discussion, Review/Audit, artifacts и зависимостями. Внешние системы подключаются
как интеграции и источники внешних ссылок; их идентификаторы не заменяют
`TaskID`.

Этот ADR определяет identity и External References. Двусторонняя синхронизация,
конфликты полей и расписание импорта являются отдельной подсистемой и требуют
отдельного integration design.

## Решение

### Канонический TaskID

`TaskID` выдаёт Coord. Формат MVP — `task_<ULID>`, где ULID — 26 символов
Crockford Base32, канонически записанных в верхнем регистре. Парсер принимает
только эту каноническую запись; lowercase не нормализуется автоматически. ID
стабилен, не зависит от GitHub/GitLab/Jira и не меняется при добавлении,
удалении или смене внешних ссылок.

Task может существовать без External References, в том числе в offline mode.
Внутренние зависимости, workflow, события и Discussion Graph используют только
`TaskID`.

`TaskID` бизнес-непрозрачен: он не кодирует GitHub Issue ID, Jira Ticket ID,
Milestone ID, Workflow State, Repository Identity, Role или Status. ULID
содержит timestamp-компонент, поэтому по нему можно вывести приблизительное
время создания. Это допустимое техническое свойство формата для локальной
генерации и сортировки без центрального счётчика; TaskID не следует считать
средством сокрытия времени создания.

Генератор использует криптографическую случайность. В одном процессе выдача
монотонна при одинаковом или откатившемся времени за счёт увеличения entropy.
Между независимыми генераторами строгий порядок в пределах одной миллисекунды не
гарантируется; сортировка по TaskID даёт временную группировку, но не заменяет
канонический `CreatedAt` и не должна использоваться для workflow-решений. При
расхождении часов разных генераторов сортировка по ID может не совпасть с
фактическим порядком создания. Transaction boundary проверяет уникальность
TaskID до commit; при коллизии генерация повторяется.

Внешние issue numbers, ticket keys и URL не являются `TaskID`. Пользовательские
представления показывают title и подходящие External References; внутренний
ULID применяется для identity, ссылок, поиска, логирования и корреляции.

### ExternalReference

```go
type ExternalReference struct {
    TaskID      TaskID
    Provider    string
    Instance    string
    ExternalID  string
    Status      ExternalReferenceStatus
    PriorStatus *ExternalReferenceStatus  // непусто только когда Status == DELETED_EXTERNAL; хранит статус для восстановления без чтения журнала
    Metadata    map[string]any
}
```

`PriorStatus` устанавливается атомарно при переходе в `DELETED_EXTERNAL` и очищается при восстановлении. Восстановление обязано использовать `PriorStatus`, а не вычислять прежний статус из внешних данных. При сохранении `PriorStatus` в snapshot оба поля — `Status` и `PriorStatus` — входят в одну durable transaction.

`Provider + Instance + ExternalID` задают уникальную внешнюю идентичность в
пространстве конкретной интеграции. `Instance` различает публичные и частные
инсталляции, например `github.com` и `github.company.local`. `ExternalID` —
неизменяемый provider-native ID в этом пространстве. Человекочитаемые номера,
ticket keys и URL служат для поиска/отображения и не заменяют provider-native
identity, когда у провайдера есть стабильный ID.

Один Task может иметь несколько External References. Один внешний объект может
быть привязан не более чем к одному Task. Повторное связывание того же
`Provider + Instance + ExternalID` с другим Task отклоняется как конфликт.
Запрет действует во всех статусах, включая `ARCHIVED` и `DELETED_EXTERNAL`:
архивирование связи не освобождает внешнюю идентичность для другого Task. Иначе
история расходилась бы с канонической идентичностью, а прежняя Task потеряла бы
провенанс объекта. Перенос одного объекта между Tasks — отдельное решение, а не
побочный эффект повторного связывания.

`EXT-06` опирается на нормализацию `Provider` и `Instance`: уникальность
`(Provider, Instance, ExternalID)` имеет смысл только для канонической записи.
Минимальное правило: host приводится к нижнему регистру и без схемы и без
дефолтного порта; `Instance` для публичного сервиса — канонический host, для
приватного — канонический host инсталляции; пустой `Instance` у конкретного
провайдера отклоняется, потому что «GitHub» и «github.com» иначе создадут две
записи об одном объекте. До принятия правила добавление ссылки с
неканонической записью `Provider`/`Instance` отклоняется fail-closed, а не
нормализуется молча.

`Metadata` хранит только интеграционные атрибуты или наблюдённый snapshot с
указанным источником и временем получения. Он не становится каноническим
workflow-состоянием и не изменяет поля Task сам по себе. Ключи `Metadata`
ограничены строками; значения — примитивы, массивы примитивов или одноуровневые
объекты. Вложенные структуры произвольной глубины отклоняются при приёме команды.
Конкретная JSON Schema `Metadata` задаётся per-provider integration spec и не
определяется этим ADR.

### Владение полями и синхронизация

По умолчанию Coord владеет `TaskID`, title/description Task, workflow, Runs,
Review, Audit, Discussion и зависимостями проекта.

GitHub, GitLab или Jira остаются источниками своих внешних полей, например
issue metadata, comments и labels. Если Coord их импортирует, импорт является
явно помеченным наблюдением/проекцией с provenance и временем получения. Он не
перезаписывает канонические поля Coord без отдельной принятой ownership/sync
policy. Двусторонняя синхронизация и разрешение конфликтов полей не определяются
этим ADR.

### Жизненный цикл ссылки

Допустимые статусы:

- `ACTIVE` — ссылка разрешается и внешняя запись считается доступной;
- `ARCHIVED` — связь больше не используется для текущей работы, но сохранена
  для истории;
- `DELETED_EXTERNAL` — провайдер подтвердил удаление внешнего объекта;
- `BROKEN` — вычисляемая проекция последней неуспешной проверки ссылки; это не
  канонический lifecycle status и не доказательство удаления.

Поле канонической `ExternalReference.Status` хранит только `ACTIVE`, `ARCHIVED`
или `DELETED_EXTERNAL`. API может показывать вычисленный `BROKEN` вместе с
`last_checked_at`, причиной и freshness.

Удаление или недоступность внешнего объекта не удаляет Task. Внешнюю ссылку не
удаляют физически из истории: её можно архивировать, а подтверждённое удаление
отражается статусом. Временная ошибка сети/авторизации не переводит ссылку в
`DELETED_EXTERNAL`.

Критерий подтверждённого удаления определён per provider и не выводится из
одного кода ответа. HTTP 404 доказывает удаление только если провайдер
различает удалённый и недоступный объект; у GitHub, например, оба случая
возвращают 404, поэтому сам по себе он не является доказательством. 403,
rate-limit, таймаут и сетевая ошибка доказательством не являются никогда.
Пока критерий провайдера не определён и не принят, `DELETED_EXTERNAL` не
выставляется автоматически: наблюдение остаётся в вычисляемом `BROKEN` с
причиной и временем. Критерий хранится рядом с интеграцией, а не выводится из
настроек Coord по умолчанию.

Допустимые переходы канонического `Status`:

| Из | Условие | В |
|---|---|---|
| `ACTIVE` | OWNER-команда, связь больше не нужна | `ARCHIVED` |
| `ARCHIVED` | OWNER-команда, связь снова нужна | `ACTIVE` |
| `ACTIVE` или `ARCHIVED` | Провайдер вернул подтверждение удаления по критерию ниже | `DELETED_EXTERNAL` |
| `DELETED_EXTERNAL` | Провайдер вернул объект, то есть ссылка снова разрешается | Прежний статус до `DELETED_EXTERNAL`, то есть `ACTIVE` или `ARCHIVED` |

Каждый переход записывается доменным событием в той же transaction. Обратный
переход из `DELETED_EXTERNAL` требует нового подтверждения разрешения, а не
только снятия статуса вручную. Переход в `BROKEN` каноническим переходом не
является: это вычисляемая проекция наблюдения.

Восстановление возвращает именно прежний статус, а не всегда `ACTIVE`. Внешний
сигнал провайдера не имеет права отменить решение OWNER об архивировании: если
связь была `ARCHIVED`, пропала и вернулась, она остаётся `ARCHIVED`, и вернуть
её в `ACTIVE` может только отдельная OWNER-команда. Прежний статус хранится в
самом событии `EXTERNAL_REFERENCE_DELETED_EXTERNAL` и, для восстановления из
snapshot без чтения журнала, в поле `PriorStatus`; восстановление обязано
использовать сохранённое значение, а не текущее состояние внешнего объекта.

### Граница с Project Dependency Graph

ExternalReference отвечает на вопрос «какой внешний объект связан с Task для
интеграции или навигации?». Она не является ребром Project Dependency Graph и
не подразумевает `DEPENDS_ON`, `BLOCKS` или другой проектной связи.

Project Map использует типизированные `GraphNodeRef` и `GraphEdge` согласно
ADR-0002. ADR и Milestone как узлы roadmap разрешаются через реестр документов/
записей проекта. Если Task относится к ADR, эта проектная связь представляется
GraphEdge. При необходимости тот же ADR может также присутствовать как
ExternalReference для навигации: ExternalReference идентифицирует внешний
документ, а GraphEdge выражает смысловую связь в roadmap. Эти записи не заменяют
друг друга и не порождают автоматически друг друга. Startup Card может показать
внешние ссылки Task и связанные ADR как отдельные поля контекста.

## События и атомарность

Изменение связи записывается в Coord доменными событиями:

- `EXTERNAL_REFERENCE_ADDED`;
- `EXTERNAL_REFERENCE_UPDATED` — изменены изменяемые атрибуты/metadata, но не
  ключ внешней идентичности; поля `Provider`, `Instance` и `ExternalID` неизменяемы
  после `EXTERNAL_REFERENCE_ADDED`; попытка изменить их отклоняется как конфликт;
- `EXTERNAL_REFERENCE_ARCHIVED`;
- `EXTERNAL_REFERENCE_DELETED_EXTERNAL` — подтверждённое удаление у провайдера;
  событие фиксирует прежний статус ссылки, к которому она вернётся при
  восстановлении;
- `EXTERNAL_REFERENCE_RESTORED` — выход из `DELETED_EXTERNAL` по подтверждению
  провайдера, с возвратом прежнего статуса;
- `EXTERNAL_REFERENCE_REACTIVATED` — OWNER-команда `ARCHIVED` → `ACTIVE`.

Акторам соответствуют разные события: восстановление приходит от внешнего
провайдера, реактивация — от OWNER. Смешивать их в одно событие нельзя, потому
что тогда в журнале не видно, было ли возвращение подтверждением провайдера или
решением OWNER.

### Идентичность доказательства провайдера

Событие `EXTERNAL_REFERENCE_DELETED_EXTERNAL` и `EXTERNAL_REFERENCE_RESTORED`
обязано содержать `ProviderEvidenceID` — стабильный идентификатор подтверждающего
сигнала от провайдера (например, webhook delivery ID, event ID или URL конечной точки).
`ProviderEvidenceID` хранится в событии для аудита и позволяет сопоставить доменное
событие с провайдерским логом. Одинаковый `ProviderEvidenceID` в двух командах —
дубликат; повторная обработка отклоняется (idempotent по evidence ID). Без
`ProviderEvidenceID` команда отклоняется fail-closed.

### Порядок обработки команд и replay

Команды External Reference обрабатываются в порядке: авторизация → проверка
идентичности задачи → проверка уникальности `(Provider, Instance, ExternalID)` →
replay lookup по ProviderEvidenceID или MessageID → сверка ожидаемой Revision →
проверка инвариантов → один durable commit. Replay состояния при восстановлении из
snapshot использует `Status` и `PriorStatus` из snapshot; чтение полного журнала
для восстановления прежнего статуса запрещено.

`BROKEN` вычисляется из ограниченного по времени resolver observation и не
изменяет lifecycle state External Reference. Успешная проверка снимает проекцию;
таймаут, отказ авторизации или временная недоступность не являются подтверждением
удаления. Resolver observations могут фиксироваться как диагностические события
с причиной и временем проверки через тот же daemon command path по ADR-0004, но
не изменяют Task или жизненный цикл ссылки. Прямой resolver write в storage
запрещён.
Изменения канонической ссылки (добавление, обновление изменяемых атрибутов,
архивация, подтверждённое удаление) и соответствующий DomainEvent сохраняются
одной durable transaction согласно ADR-0001. Физическое удаление ссылки из
event history запрещено.

## API и Startup Card

> **Целевой контракт.** Task API и Resolver API, описанные в этом разделе, задают
> целевую форму read-only boundary. Конкретные маршруты, авторизация и versioning
> определяются ADR-0006. До принятия и реализации ADR-0006 эти endpoints не
> являются product capability.

Task API возвращает стабильный `TaskID` и список External References. Resolver
API может находить Task по `(Provider, Instance, ExternalID)`, но точные маршруты,
авторизация и versioning закрепляются в API design (ADR-0006).

Startup Card показывает `TaskID` как рабочую идентичность и внешние ссылки как
контекст, например:

```yaml
task:
  id: task_<ULID>
  title: Duplicate protection

external_refs:
  - provider: github
    instance: github.com
    external_id: I_kwDOABc12345
    display: crewflow#251
    status: ACTIVE

related_roadmap_nodes:
  - kind: ADR
    id: ADR-0001
```

Агент ссылается на `TaskID` в командах Coord и не использует issue number или
ticket key как идентичность Task. Он не выводит из структуры TaskID возраст,
приоритет, этап workflow или иное бизнес-решение.

## Инварианты

- **EXT-01:** `TaskID` принадлежит Coord, стабилен и никогда не выводится из
  внешнего идентификатора.
  Проверка: не реализовано
- **EXT-02:** удаление внешнего объекта не удаляет Task.
  Проверка: не реализовано
- **EXT-03:** Task может иметь ноль или более External References.
  Проверка: не реализовано
- **EXT-04:** External References и Project Dependency Graph — разные модели.
  Проверка: не реализовано
- **EXT-05:** External References не владеют Task workflow.
  Проверка: не реализовано
- **EXT-06:** `(Provider, Instance, ExternalID)` уникален и связан максимум с
  одним Task.
  Проверка: не реализовано
- **EXT-07:** Workflow, Runs, события и графы используют канонический `TaskID`.
  Проверка: не реализовано
- **EXT-08:** импортированные внешние поля не меняют каноническую Task без
  отдельной принятой ownership/sync policy.
  Проверка: не реализовано
- **EXT-09:** состояние External Reference и событие его изменения фиксируются
  атомарно; потеря внешней доступности не стирает историю.
  Проверка: не реализовано
- **EXT-10:** подтверждение провайдера не отменяет решение OWNER: восстановление
  из `DELETED_EXTERNAL` возвращает прежний статус из события или поля
  `PriorStatus`, а `ARCHIVED` → `ACTIVE` выполняется только OWNER-командой.
  Проверка: не реализовано
- **EXT-11:** команды External Reference проходят canonical command boundary:
  авторизация → проверка субъекта → проверка идентичности задачи → проверка
  уникальности `(Provider, Instance, ExternalID)` → replay lookup по
  ProviderEvidenceID или MessageID → сверка ожидаемой Revision → проверка
  инвариантов → один durable commit. Ни один write не обходит эту границу.
  Проверка: не реализовано
- **TID-01:** генератор ULID обеспечивает уникальность с пренебрежимо малой
  вероятностью коллизии между независимыми процессами; он гарантирует
  монотонность только внутри одного процесса. Фактически сохранённые TaskID
  строго уникальны в Coord: transaction boundary проверяет уникальный ключ под
  exclusive ownership snapshot backend либо через native unique constraint
  transactional backend. При коллизии Coord повторяет генерацию до записи
  связанного события и Outbox.
  Проверка: частично — `TestGeneratorConcurrentCallsAreUnique`, `TestGeneratorIsMonotonicForRepeatedAndBackwardClock`; не реализовано: уникальный ключ TaskID при сохранении
- **TID-01a:** исчерпание 80-битной случайной компоненты ULID в пределах одной
  миллисекунды не лечится повтором в той же миллисекунде. ULID содержит 48-битный
  timestamp и 80-битный случайный компонент; при монотонном инкременте 80-битный
  счётчик может переполниться. Генератор возвращает ошибку при переполнении, и
  Task не записывается. Повтор допустим только с более поздним timestamp. Это
  ограничение монотонного ULID в одном процессе и не является коллизией entropy
  между независимыми генераторами (TID-01).
  Проверка: частично — `TestGeneratorFailsWhenMonotonicEntropyOverflows`; не реализовано: Task не записывается при ошибке генератора (Task aggregate нет)
- **TID-02:** TaskID неизменен в течение жизни Task.
  Проверка: не реализовано
- **TID-03:** TaskID не зависит от внешней системы или её идентификаторов.
  Проверка: не реализовано
- **TID-04:** TaskID не кодирует бизнес-семантику.
  Проверка: не реализовано
- **TID-05:** TaskID может содержать технические данные для генерации и
  упорядочивания; ULID раскрывает приблизительное время создания.
  Проверка: не реализовано
- **TID-06:** формат MVP — `task_<ULID>` с каноническим Crockford Base32.
  Проверка: `TestParseRejectsNonCanonicalIDs`, `TestGeneratorProducesCanonicalRoundTrippableID`

## Последствия и открытые решения реализации

- Coord не зависит от номера issue или конкретного forge для идентичности Task.
- Перенос между системами добавляет/архивирует External References, сохраняя
  `TaskID` и историю.
- До реализации нужно определить нормализацию `Provider/Instance`, источник и
  регистрацию ADR/Milestone, интеграционные resolver маршруты и storage schema.
- Текущий импорт, двусторонняя синхронизация, политика полей и UI отображения
  нескольких ссылок требуют отдельных design решений.
