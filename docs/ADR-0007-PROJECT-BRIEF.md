# ADR-0007: Project Brief и Task Brief

- **Статус:** Proposed
- **Область:** производные представления уровня проекта и задачи, отдаваемые по запросу
- **Связанные решения:** ADR-0001 Canonical Coordination Model (производные представления); ADR-0004 Runtime and Daemon Model (RT-03); ADR-0005 Storage Model (ST-01)
- **Ближайшее решение:** Startup Card и read-only API определяются в ADR-0006 API
  Contract, который ещё не написан. Номер 0006 зарезервирован за ним, поэтому этот
  документ его не занимает. Brief подключается к API после появления ADR-0006.

## Назначение

Ранняя редакция этого документа утверждала, что «Coord уже отдаёт
производные представления: `RunViewStatus` считается на лету». Это не соответствует
коду, и утверждение разделено на три разные вещи.

1. **`RunViewStatus` в коде нет.** Идентификатора `RunViewStatus` нет ни в одном
   Go-файле репозитория; он существует только как норма TASK-MODEL TM-14
   («только вычисляемое представление для человека»), у которой собственная
   аннотация «Проверка: не реализовано». Coord не отдаёт такой проекции ни во
   внутреннем API, ни наружу.
2. **Что вычисляется на лету фактически.** В legacy rooms вычисляется проекция
   сессии, а не Run: `internal/rooms/sessions.go` собирает `State`, `Attachment`,
   `Reachability`, `Readiness`, `Processing`, `LastActivity` и
   `ProviderAvailability` из сохранённых фактов, включая различение поколений по
   `latestCredentialGeneration` (`:315-335`, набор полей `:265-274`); проверки —
   `TestSessionRecoveryFencesAndScopesContext`,
   `TestAvailabilitySeparatesStaleGeneration`. В daemon вычисляется причина
   not-ready из transport-готовности и наличия recovery
   (`daemon/daemon.go:107-115`, проверка `TestDaemonReadinessLifecycle`), а
   control endpoint `/runs` фильтрует stalled-результаты по сохранённому Run без
   вычисляемой проекции (`control.go:27-36`). Ни одно из этих наблюдений не
   является `RunViewStatus` и не подтверждает его существование.
3. **Отсутствие read interface для Task и будущий Task Brief.** Read-only API
   Task не написан: ADR-0006 не существует, и ни один endpoint не отдаёт проекцию
   Task (см. §MVP). При этом внешний control interface у daemon есть — bearer-token
   handler (`control.go:20-36`), чей `GET /runs` возвращает только stalled-результаты
   для supervisor recovery; это не `RunViewStatus` и не проекция Task, и наличие
   этого endpoint'а не означает read-only Task API. Task Brief остаётся контрактом
   целевого ADR-0007 (Proposed).

Brief продолжает линию вычисляемых по запросу проекций для уровня задачи и
проекта. В канонической модели таких проекций пока нет; проекция сессии в
`internal/rooms` относится к legacy (ADR-0001, «Миграция от `internal/rooms`»,
`:504-529`) и опорой для Brief не служит.

Термин **snapshot** зарезервирован за storage snapshot из ADR-0005. Brief никогда
не называется snapshot, чтобы не смешивать проекцию, читаемую по запросу, с
каноническим состоянием, из которого читается recovery.

## Виды Brief

**Live Brief** — проекция, вычисляемая по запросу из канонического состояния.
Не хранится, не версионируется, не является источником истины. Для одной и той же
ревизии state результат детерминирован: тот же вход даёт тот же выход, поэтому
два чтения без изменения state дают одинаковый Brief.

**Archived Brief** — неизменяемая запись того, что было показано: ревизия
источника, версия генератора и хеш содержимого. Воспроизводимость задним числом
не обещается: по ST-01 журнал не пересобирает состояние, поэтому повторная генерация
Archived Brief для той же ревизии может дать иной текст при изменившемся генераторе.
Archive фиксирует факт показа, а не воспроизводимость.

## MVP

В MVP только **Task Brief** в форме Live Brief, и только из данных Task и Run.
Требования, без которых его не на чем построить: TaskID adoption, production
daemon по ADR-0004 и Task aggregate по ADR-0001. Их фактическое состояние на
2026-10-08: TaskID adoption реализован (`taskid.New`, `taskid.ID`,
`TestCreateTaskGeneratesCanonicalTaskID`), канонический Task aggregate со связью
Task ↔ Run, `Task.Fence` и историей DomainEvent — тоже
(`store/canonical.go:67-74`, `TestCanonicalStateValidatesTaskEventAndRunRelations`,
`TestCanonicalStoreRejectsTaskMutationWithoutEvent`), standalone daemon существует,
но его приёмка не закрыта (`cmd/coordd/main.go`,
`TestCoorddTakesNamespaceLockBeforeStores`, ROADMAP: P0-1 OPEN).

Поэтому MVP Brief остаётся контрактом, а не функцией, но по другой причине, чем
указано в ранней редакции этого документа: данных Task и Run теперь достаточно,
а отсутствует read-only API для Task — ADR-0006 не написан, и ни одна проекция
уровня Brief не выдаётся ни одним существующим endpoint. Внешний control endpoint
daemon (`control.go:20-36`) отдаёт только stalled-результаты для supervisor
recovery и проекцией Task не является. Статус этого ADR остаётся Proposed, и
зрелость Brief не повышается.

## Вне MVP

Перечисленные виды отложены, и у каждого отсутствует канонический источник. Пока
источника нет, Brief такого вида не создаётся вовсе, даже в частичном виде.

- Project-wide Brief — нет канонического состояния уровня проекта.
- Archived Brief — нет принятой политики хранения и срока.
- Roadmap summary — нет принятого правила ранжирования (см. Summary).
- Risk registry — нет канонического Risk объекта.
- Project-level Decision — решения владельца живут в Task, а не в проекте.
- Defect registry — дефекты пока живут в markdown, а не в канонических событиях.
- Наблюдения git/CI — нет канонического наблюдения, только внешние системы.
- API — ADR-0001 откладывает API до готовности canonical write path.
- Dashboard — читает API, а не каноническое состояние.

## Инварианты

- **BR-01 — только проекция.** Brief вычисляется из канонического состояния и
  никогда не становится его источником.
  Проверка: не реализовано
- **BR-02 — нет уникальных данных.** Brief не содержит сведений, которых нет в
  источнике. Всё, чего нет в источнике, отсутствует и в Brief.
  Проверка: не реализовано
- **BR-03 — не используется для recovery и replay.** Ни один переход, проверка
  инварианта и восстановление не читают Brief. Journal не переигрывает его.
  Проверка: не реализовано
- **BR-04 — ссылка на источник у каждого элемента.** Каждый пункт Brief несёт
  ссылку на конкретный факт, из которого он получен: Task, Run, Discussion node
  или edge. Пункт без ссылки не попадает в Brief.
  Проверка: не реализовано
- **BR-05 — детерминированный порядок.** Порядок задаётся правилом, а не
  выбором реализации. Один и тот же набор источников даёт один и тот же порядок.
  Проверка: не реализовано
- **BR-06 — нет прогнозов.** Brief не содержит предсказаний, оценок сроков и
  рекомендаций. Только факты текущего состояния.
  Проверка: не реализовано
- **BR-07 — UNKNOWN при недостоверности.** Если источник недостоверен, устарел или
  отсутствует, элемент получает явное значение UNKNOWN с причиной. Молчаливое
  отсутствие недопустимо: читатель должен отличать «факта нет» от «факт есть и
  равен UNKNOWN».
  Проверка: не реализовано
- **BR-08 — генерация вне транзакции.** Brief строится вне command boundary
  fencing и вне транзакций recovery по RT-03. Отказ генерации Brief не влияет на
  прохождение recovery, readiness и публикацию нового состояния: Brief —
  читаемое представление, а не условие записи.
  Проверка: не реализовано
- **BR-09 — доступ по текущему назначению.** Task Brief читают OWNER и сессии с
  действующей Task-scoped capability текущего назначения: актуальная generation,
  capability не отозвана. Исторический владелец Run и отозванная сессия доступа
  не получают Task Brief.
  Проверка: не реализовано
- **BR-10 — Project Brief только для OWNER.** Ни один агент и ни одна сессия Task
  не читают Project Brief.
  Проверка: не реализовано
- **BR-11 — ORCHESTRATOR не принципал доступа.** ORCHESTRATOR — внутренняя
  функция Coord: она читает каноническое состояние напрямую и не запрашивает
  Brief. Brief не выдаётся принципалу по признаку этой функции.
  Проверка: не реализовано

## Доступ

**Task Brief** доступен OWNER и тем сессиям, у которых есть действующая
Task-scoped capability **текущего** назначения: актуальная generation, не
отозванная capability. Правило выведено из дефекта, найденного при аудите
localchat: агент с действующим `Auth` получал 403 на owner-эндпоинты, пока
`/events` не был ошибочно выведен из списка не-owner — тогда агент читал полный
журнал комнаты, включая текст задачи и назначения. Вывод: агентский доступ
ограничен scope его Task, а не всем проектом.

Исторические владельцы Run и отозванные сессии доступа к Task Brief не имеют.
Прошлое назначение не выдаёт доступа после смены назначения. Агент, которому
нужна история, получает её через Startup Card **текущего** назначения, а не
через сохранённый доступ.

**Project Brief** доступен только OWNER, поскольку отражает проект в целом, а не
работу конкретного агента.

`ORCHESTRATOR` — внутренняя функция Coord, а не внешний принципал доступа, и в
список читателей Brief не входит. Функция ORCHESTRATOR читает каноническое
состояние напрямую, как другие внутренние функции, и сама Brief не запрашивает.
OWNER получает Project Brief через авторизованный read path daemon (ADR-0004
RT-05; контракт — ADR-0006, ещё не написан).

**Startup Card агента** ссылается только на Task Brief. Это не ограничение
удобства, а следствие границы доступа: карточка передаётся агенту и не должна
приносить проектные сведения шире его Task.

## Summary

Summary — не более трёх пунктов. Пункт попадает в Summary только если
соответствует принятому правилу ранжирования. Пока правило не принято, Summary
не генерируется вовсе: ручной отбор трёх пунктов — это скрытое редакторское
решение, которое невозможно воспроизвести и проверить.

## Последствия

- Документ фиксирует контракт производного представления, а не реализацию.
- MVP требует Task aggregate, поэтому до его появления Task Brief не строится.
- Инвариант BR-08 сохраняет разделение: сбой представления не должен блокировать
  запись состояния.
- Правило ранжирования Summary остаётся открытым и должно быть принято отдельно.

## Открытые вопросы

- Правило ранжирования для Summary и кто его принимает.
- Политика хранения и срок жизни Archived Brief, если Archive вообще понадобится.
- Канонический источник Risk, project-level Decision и Defect.
- Срок реализации Task Brief: после Task aggregate или вместе с ним.

## Критерии соответствия

Реализация соответствует этому ADR, если:

- Brief не хранится в snapshot и не участвует в записи состояния (BR-01, BR-02);
- ни один переход, проверка инварианта и восстановление не читают Brief (BR-03);
- каждый пункт Brief имеет ссылку на источник (BR-04);
- порядок элементов задаётся правилом и воспроизводим (BR-05);
- Brief не содержит прогнозов, оценок сроков и рекомендаций (BR-06);
- UNKNOWN выводится явно, а не молчаливым отсутствием (BR-07);
- Task Brief не выдаётся сессии без действующей Task-scoped capability текущего
  назначения: актуальная generation и неотозванная capability, а исторический
  владелец Run и отозванная сессия доступа не получают (BR-09);
- Project Brief не выдаётся вне OWNER (BR-10);
- ORCHESTRATOR как внутренняя функция Coord в список читателей Brief не входит и
  читает каноническое состояние напрямую (BR-11);
- OWNER получает Project Brief через авторизованный read path daemon, а не через
  внутренний доступ (BR-10);
- генерация Brief идёт вне транзакции fencing и recovery (BR-08);
- отказ генерации Brief не влияет на recovery и readiness (BR-08);
- Summary не генерируется до принятия правила ранжирования;
- Live Brief не хранится и детерминирован для одной ревизии state;
- Archived Brief фиксирует ревизию источника, версию генератора и хеш
  содержимого и не обещает воспроизводимости задним числом.
