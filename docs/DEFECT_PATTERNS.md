# Defect Patterns Ledger

Реестр повторяющихся классов дефектов, а не список отдельных багов. Класс
попадает сюда, если повторился в нескольких компонентах. У каждого класса есть
механизм, который должен его ловить, и статус автоматизации:

- `FULL` — класс ловится автоматически во всех известных местах;
- `PARTIAL` — автоматически ловятся отдельные случаи, общего механизма нет;
- `NONE` — автоматической проверки нет.

Пустых полей нет: отсутствие проверки записывается как «не автоматизировано».
Запись без проверяющего механизма сама становится источником дрейфа (DP-003).

Основание — аудит рабочего дерева 2026-10-07 (Claude Code, Codex, OpenCode).
Примеры описывают состояние на момент аудита; часть может быть исправлена
параллельной работой — сверяйтесь с кодом и тестами, а не с этим списком.

## Вопросы для review

Новый тест, ADR или пункт CHANGELOG проходит review с вопросами:

1. Какая мутация кода должна сломать этот тест? (DP-001)
2. Что из прежнего состояния и какие ресурсы должны исчезнуть после перехода? (DP-002)
3. Где ещё записано это правило, и что проверяет их совпадение? (DP-003)
4. С какими уже принятыми документами пересекается это правило? (DP-004)
5. Остаётся ли состояние неизменным при отказе в валидации? (DP-005)

## DP-001 — Косвенный признак вместо инварианта

**Описание.** Тест наблюдает побочный эффект, который обычно сопутствует
гарантии, и проходит, когда гарантия нарушена.

**Примеры.**

- `kill(-pgid, 0)` как доказательство «writer перестал писать»: zombie остаётся
  членом группы до reap, проверка флакала; ранее тест не отличал остановку
  лидера от остановки всей группы.
- Появление последней реплики как доказательство «без потерь и по порядку»;
  порядок не проверялся.
- Счётчик дублей через `strings.Contains` (не больше 1 на кадр) — проверка не
  могла сработать.
- HTTP 200 на повтор как доказательство идемпотентности, хотя повтор
  перезаписывал `ObservedAt` и добавлял событие в журнал.
- Тест «ожидание просыпается на событии» проходил без пробуждения: событие
  могло быть записано до начала ожидания.
- Горутина теста при ошибке молча завершалась, тест проходил без проверки.
- `time.Sleep` как доказательство отсутствия события.
- Защитная проверка продублирована (до lock и внутри update): удаление любой
  одной копии не ломает ни один тест, поэтому ни одна копия не защищена.
- `Process.Close` считал отмену «своей» только по `*exec.ExitError`; штатный
  выход MCP-сервера с кодом 0 раньше kill давал `context canceled`, тест падал
  в 122 из 200 прогонов, а одиночные прогоны выглядели зелёными.

- В документах: нумерация правил превратила каждый абзац в «правило» с
  именем раздела вместо имени нормы (CM-03 «Решение. `Task`»); совпадение
  слов до и после доказывало только отсутствие потерь, а не то, что номер
  обозначает проверяемую норму.
- Обратная форма в ревью: «control API открыт при not-ready» выведено из
  формы guard (один bool на весь handler), хотя все маршруты были recovery-only
  и разрешены ADR-0004 RT-03. Второй ревьюер «подтвердил независимо», повторив
  рассуждение, а не проверив, что делают маршруты.

**Почему опасно.** Зелёный тест подтверждает гарантию, которой нет. Дефект
обнаруживается в эксплуатации, а VERIFICATION.md объявляет его закрытым.
Для ownership и fencing это прямой путь ко второму writer.

**Механизм обнаружения.**

- Negative control: до действия тест подтверждает, что свойство ещё не
  выполнено или ресурс жив; после — что выполнено.
- Отсутствие события доказывается синхронизацией по факту (lock, EOF, seq,
  cursor, счётчик), а не паузой.
- Mutation testing: для каждой строки VERIFICATION.md указан дефект, который
  тест обязан поймать.
- У каждой копии защитной проверки свой тест; копия без теста удаляется.

**Automation Status:** `PARTIAL`.

**Связанные тесты.**

- `internal/telepathyhost.TestWorkerAbortStopsWriterProcessGroup`,
  `TestWorkerLeaseLossStopsWriterProcessGroup` — writer держит flock;
  освобождение lock доказывает закрытие его fd независимо от reap.
- `internal/localchat.TestDeliverEventWakesOnRoomCancelWhileQueueIsFull` —
  детерминированно, без зависимости от планировщика.
- `telepathy.TestCloseAfterCleanExitIsNotAnError` — синхронизация по файлу-
  маркеру выхода, а не по таймауту; мутация «флаг собственной отмены не
  выставлен» валит тест.
- `internal/localchat.TestShownEventsAreNotRedisplayedAfterRoomSwitch` —
  заменяет мёртвую проверку `strings.Contains`; мутация «курсор не
  подтверждается» даёт повтор показанного события и валит тест.
- `internal/localchat.TestAgentAuthCannotReadOwnerEndpoints` — negative
  control: сначала валидный Auth агента получает 200 в своём scope, затем 403
  на owner-эндпоинтах; иначе 403 доказывал бы лишь битый Auth.
- Не автоматизировано: запрет sleep-ожиданий отсутствия; связь строк
  VERIFICATION.md с мутациями.

**Связанные ADR.** ADR-0001 «Run, Attempt и Fence» (stop proof до передачи
writer); ADR-0004 RT-06 Task-wide Fencing и «Process Ownership».

## DP-002 — Переход не очищает зависимое состояние или ресурс

**Описание.** Переход реализован точечной записью полей; производные поля и
ресурсы владельца остаются от прежнего состояния.

**Примеры.**

- Дедлайн делал run терминальным, но оставлял `RecoveryClaim`.
- `/join` другой комнаты оставлял открытой подписку `/watch` прежней.
- Горутина чтения ввода оставалась на отправке после `/quit`.
- Daemon: флаг `started` конфликтовал с `Close`, `ShutdownTimeout` расходовался
  дважды, readiness не учитывала ownership/recovery.
- Writer process group переживал остановку лидера.
- Дедлайн делал run `FAILED`, но оставлял `ResumeStatus` — точку продолжения
  терминального run.
- Выход из `STALLED` (поздний heartbeat или RESULT после пропущенного probe)
  оставлял `ResumeStatus`; исправлено в единственной точке `fsm.Run.Apply`.
- Блокер квоты привязан к session, а квота — к agent/provider: новый `Assign`
  того же агента создаёт сессию без блокера.

**Почему опасно.** Снимок показывает активный claim у мёртвого run, события
уходят не в ту комнату, ресурсы утекают. Противоречивые поля — «Task говорит
A, Attention говорит B» — подрывают единственный источник истины.

**Механизм обнаружения.**

- Одна функция инвариантов агрегата (terminal ⇒ нет claim/lease/recovery),
  которую тесты вызывают после каждой операции.
- Производное значение по возможности вычисляется проекцией, а не хранится.
- Горутина, подписка или процесс создаётся с context владельца; тест считает
  живые ресурсы после смены владельца. Проекция ресурсы не освобождает.
- Для нового состояния документ называет его scope и ключ
  (session, agent, provider, task).

**Automation Status:** `PARTIAL`.

**Связанные тесты.**

- `coord.TestDeadlineAfterClaimClearsRecoveryClaim`
- `internal/localchat.TestRoomSwitchCancelsWatchSubscription`
- `internal/localchat.TestQuitWithTrailingInputLeavesNoGoroutine`
- `examples/agent.TestLocalAgentDeadlineStopsDescendantWriter`
- `coord.TestRunInvariantsHoldThroughLifecycle` — `checkRunInvariants`
  (Terminal ⇒ нет RecoveryClaim/RecoveryNeeded, claim только у Stalled с
  RecoveryNeeded, Done ⇒ Result) после каждого шага жизненного цикла и
  межшаговые правила: Attempt не меняется при повторной доставке, Fence не
  убывает, Terminal не возвращается. Нашёл остаточный `ResumeStatus` у
  `FAILED` после дедлайна.
- `coord.TestStalledExitClearsResumeStatus` — оба выхода из `STALLED`;
  мутация «очищать только на терминальном переходе» валит тест.
- Не автоматизировано: такие же инварианты для Task/Room/Session; вызов
  `checkRunInvariants` из остальных сценарных тестов.

**Связанные ADR.** ADR-0001 «Производные представления»; ADR-0004 RT-01
Single Owner, RT-03 Recovery и readiness; TASK-MODEL «Stage transitions».

## DP-003 — Два источника правды расходятся

**Описание.** Одно правило записано в двух местах (client и handler, документ
и код, два документа), и одна копия отстаёт.

**Примеры.**

- Разные таблицы HTTP-методов в client и handler дали 405 на `/availability`.
- CHANGELOG и тексты ошибок предписывали `coord session unblock`, которой нет
  в CLI.
- Примеры ADR-0002 использовали числовые TaskID вопреки `task_<ULID>` из
  ADR-0003.
- ALIGNED_UX требует проверку checkpoint при снятии блокера; код её не делает.
- CHANGELOG обещал освобождение горутины ввода по `/quit` безусловно; это верно
  только при блокировке на отправке, не на чтении stdin.

**Почему опасно.** Оператор выполняет предписанное действие и получает ошибку;
реализатор читает устаревшую копию как норму.

**Механизм обнаружения.**

- Нельзя ссылаться на команду, которую не принимает parser CLI: contract-тест
  прогоняет команды из docs, README, ADR, help и строк Go через parser.
- Одно определение и генерация вместо двух списков.
- Одно правило — один владеющий документ; остальные документы ссылаются на
  его идентификатор. Тест ссылок ловит повторное определение одного ID, но не
  одно правило под двумя разными ID (CM-07 и TM-24): это проверяет только
  review по смыслу.
- Утверждение о поведении в CHANGELOG ссылается на тест; без теста оно
  помечается как непроверенное.
- Пример идентификатора либо проходит parser, либо явно помечен как
  заполнитель.

**Automation Status:** `PARTIAL`.

**Связанные тесты.**

- `internal/localchat.TestCommandMethodsAgreeBetweenClientAndHandler`
- Не автоматизировано: contract-тест команд против parser CLI; связь
  CHANGELOG с тестами; проверка примеров идентификаторов в документах.

**Связанные ADR.** ADR-0001 «Модель и инварианты» (один владелец канонических
данных); ADR-0003 TID-06 (формат TaskID).

## DP-004 — Принятые документы не сверяются между собой

**Описание.** Каждый документ проверен отдельно, но правило на границе двух
документов не записано ни в одном.

**Примеры.**

- TASK-MODEL: перекрытие общих строк `BLOCKED` с `WAITING_FOR_SUPERVISOR_STOP`,
  отсутствие failure-перехода и причины not-ready.
- ADR-0002 и TASK-MODEL не определяли, влияет ли `DEPENDS_ON` на старт Task
  (закрыто DG-07).
- ADR-0002 без схемы допустимых пар узлов и рёбер; ADR-0003 без переходов
  lifecycle ссылки.
- Повтор внутри исправления: первая редакция DG-07 закрывала старт при `FAILED`
  prerequisite «до Owner-решения, меняющего граф», но в TASK-MODEL
  `OWNER_DECISION` выбирает только Stage или `COMPLETED` и граф не меняет —
  у гейта не было исполнимого пути снятия. Замена prerequisite как remove + add
  без заданной атомарности на промежуточном шаге снимала гейт; актор команд
  графа не был назван. Найдено cross-audit OpenCode; исправляется в ADR-0002
  (DG-06a, DG-07, DG-08) — проверяйте текущий текст.

**Почему опасно.** Реализация заполняет пробел своим выбором, который никто не
принимал; два Accepted-документа допускают взаимоисключающие прочтения —
например, правило требует Owner-решения, которое по другому документу
невозможно принять.

**Механизм обнаружения.**

- Перед статусом Accepted документ сверяется с уже принятыми по общим терминам
  (Task, Run, Status, Fence, TaskID) и по правилам на границе.
- Правило записывается в одном документе; остальные ссылаются на него по
  идентификатору инварианта.
- Индекс инвариантов (DG-xx, EXT-xx, TID-xx, RT-xx, ST-xx, строки переходов
  TASK-MODEL) с документом-владельцем и тестом или пометкой «не реализовано».

**Automation Status:** `PARTIAL`.

**Связанные тесты.**

- `coord.TestDocumentedInvariantsAreDefinedOnce` — каждое упоминание
  `DG/EXT/TID/RT/ST-xx` в docs, README и CHANGELOG имеет ровно одно
  определение (заголовок или пункт списка); negative control на минимальное
  число найденных определений.
- Не автоматизировано: строки переходов TASK-MODEL как идентифицируемые
  инварианты; связь инварианта с тестом или пометкой «не реализовано»;
  смысловая сверка правил на границе документов (только review).

**Связанные ADR.** ADR-0001…ADR-0005, TASK-MODEL.

## DP-005 — Валидация после чтения состояния; след при отказе

**Описание.** Валидация смешана с чтением и изменением состояния, поэтому
ошибка входа маскируется конфликтом или оставляет след.

**Примеры.**

- Некорректные reason/source/retry_at сначала возвращали 409 вместо 400.
- `retry_at` в прошлом проверялся внутри update после поиска сессии и
  авторизации (исправлено: проверка до lookup).
- JSON с хвостом мог выполнить первую операцию до отказа.
- Раньше тест `invalid_input` не проверял побочные записи; теперь blocker test
  сверяет число событий и отсутствие изменённого Blocker, но общий snapshot-hash
  helper и проверка всех invalid-input путей по-прежнему не автоматизированы.

**Почему опасно.** Клиент повторяет неизменяемый payload как конфликт; отказ
оставляет частичную запись. Для Fence, CAS и передачи ownership частичная
запись при отказе нарушает fencing.

**Механизм обнаружения.**

- Инвариант: Validation Failure = No State Mutation. Проверка входа выполняется
  до захвата lock и update.
- Для каждого пути `invalid_input` тест сравнивает снимок (hash) состояния до
  и после команды.

**Automation Status:** `PARTIAL`.

**Связанные тесты.**

- `coord.TestControlRejectsTrailingJSONBeforeMutation`
- `internal/localchat.TestSessionBlockSeparatesInvalidInputFromConflict` —
  400 против 409, без новой записи события или blocker.
- `internal/rooms.TestPastRetryAtIsInvalidInputEvenForUnknownSession` —
  неизвестная сессия + прошлый `retry_at` дают `invalid_input`, а не «сессия не
  найдена»: валидация идёт до чтения состояния.
- `internal/rooms.TestRejectedBlockerLeavesNoTrace` — хелпер
  `assertNoMutation`: сериализованный snapshot и seq комнат до и после каждого
  пути `invalidRequest` совпадают побайтно; контроль в обратную сторону —
  валидный блокер обязан изменить snapshot.
- Не автоматизировано: тот же хелпер для путей отказа вне `internal/rooms`
  (coord control, localchat HTTP, daemon); проверка, что новые пути
  `invalidRequest` попадают в таблицу теста.

**Связанные ADR.** ADR-0004 RT-04 Write Path, RT-06 Task-wide Fencing;
ADR-0005 ST-03 Commit-or-reopen, ST-06 Fencing и concurrency.
