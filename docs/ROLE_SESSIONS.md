# Устойчивые ролевые сессии Coord

Статус: архитектурное решение принято владельцем 2026-10-07.
Реализован локальный слой; команды и границы описаны в SESSION_CLI.md.
Проект самостоятельный; интеграция Crewflow находится за пределами этого решения.

## Назначение

Coord управляет совместной работой AI-агентов. Оркестратор создаёт задачи,
комнаты и назначения ролей. Owner наблюдает тот же журнал и может вмешиваться.
Telepathy — сменный канал уведомлений, а не источник истины.

## Идентичность и изоляция

Различаются task_id, room_id, session_id, agent_id и connection_id.
session_id — устойчивый UUID логической ролевой сессии. agent_id обозначает
конкретного участника; смена участника записывается отдельным событием.
connection_id и generation обозначают временное подключение.

Сессия привязана к одной комнате, роли и разрешённому контексту. Один агент
может исполнять разные роли в разных сессиях. Контекст между ними не передаётся
неявно. Совпадение агента executor и auditor должно быть видно; такое назначение
не является независимым аудитом. Оркестратор управляет разрешёнными связями
между комнатами, а не передаёт всем весь журнал.

Роль Coord не заменяет файловую песочницу или права ОС. Если два подключения
имеют доступ к одним файлам или используют общий контекст модели, журнал
и capability-токены сами по себе не обеспечивают конфиденциальность.

## Восстановление без зависимости от TUI

Любой frontend или subprocess подключается к Coord по session_id через
общий локальный API. Возвращаются назначение роли, ограничения задачи,
последний checkpoint, ссылки на артефакты и разрешённые события после cursor.
История внутреннего рассуждения модели не является требованием восстановления.

Переподключение увеличивает generation, отзывает прежний capability и
фиксирует connection_id. Изменения принимаются только от текущего поколения.
Все операции записи имеют operation_id для идемпотентного повтора.
Подтверждение получения события отличается от подтверждения выполненного действия.

Checkpoint содержит progress, pending_actions, artifact_refs и acknowledged_seq.
Для каждой pending_action сохраняются устойчивый ID и состояние выполнения.
После сбоя внешнее действие с неизвестным результатом проверяется исполнителем;
оно не повторяется автоматически на основании отсутствующего сообщения.

Смена агента требует явного назначения owner или coordinator. Новый участник
получает разрешённый контекст этой сессии и записывается в историю назначений.
Перезапуск TUI не означает смену агента. Восстановление после выключения
компьютера начинается после запуска локального Coord; автозапуск ОС — отдельная
эксплуатационная функция.

## Локальное хранение и Git

Авторитетное оперативное хранилище содержит журнал, checkpoints, поколения,
идемпотентные операции и durable outbox. Запись события и изменения состояния
происходит атомарно до подтверждения клиенту. Повторное чтение идёт по seq.

Отдельный локальный Git-репозиторий истории принадлежит единственному writer
Coord. В нём находятся экспортированные назначения, инструкции, содержательные
события, checkpoints и ссылки на результаты. Исходный репозиторий кода проекта
не используется как служебное хранилище Coord.

Git — проверяемая проекция, а не второй источник истины. Export cursor хранится
в оперативном состоянии. Commit содержит export_id и диапазон seq. Если процесс
упал после commit до записи cursor, восстановление находит этот export_id
и завершает запись cursor без повторного commit. Ошибка Git сохраняет backlog
экспорта и видна в status; уже принятое событие не исчезает.

Ключи, capability-токены, credentials и внутренние конфигурации подключения
в Git не экспортируются. Пользовательские секреты могут оказаться в тексте
сообщения: экспорт требует явной политики отбора полей и обработки секретов,
а не обещания автоматического обнаружения всех чувствительных данных.

GitLab — отдельный адаптер синхронизации. Работа и восстановление локальных
сессий не зависят от сети. Репозиторий, ветка, права и политика публикации
задаются явно. Автоматический push без настройки не выполняется.

## Минимальный публичный контракт

- rooms и sessions: устойчивые IDs, задача, роль, участник, поколение,
  последнее подтверждение, checkpoint, pending_actions и состояние подключения.
- attach/resume: session_id; возврат текущего поколения и разрешённого контекста.
- events: session_id и after_seq; только разрешённый журнал.
- ack: session_id, generation, operation_id и acknowledged_seq.
- checkpoint: session_id, generation, operation_id и состояние работы.
- say: session_id, generation, operation_id и текст.
- assign/replace: полномочия owner/coordinator и событие истории назначения.
- watch: наблюдение owner; доступ агента ограничен его назначением.
- history status/export: export cursor, последний commit, backlog и ошибки.

## Проверяемые критерии готовности

1. Два агента общаются в назначенной комнате без ручной ретрансляции owner.
2. Owner видит тот же порядок событий и может отправить реплику.
3. Один agent_id работает в двух ролях в разных сессиях без выдачи чужого контекста.
4. После остановки сервиса и клиента сохраняются IDs, роль, cursor и checkpoint.
5. Другой клиент восстанавливает ту же сессию через общий API без знания типа TUI.
6. Старое поколение не может записывать; повтор operation_id не дублирует действие.
7. Транспортный успех не продвигает acknowledged_seq.
8. Сбой на границах persist/send/ack и commit/cursor не теряет событие.
9. Git-экспорт не содержит capability и ключей; ошибка Git оставляет явный backlog.
10. Отключение GitLab не мешает локальной работе.
11. Тесты отдельно обозначают fake transport, реальный транспорт и реального AI;
    один вид проверки не выдаётся за другой.

## Реализация и границы

internal/rooms хранит устойчивые session_id, поколения, capability, checkpoints,
идемпотентные агентские операции, WAITING_ASSIGNMENT и durable outbox.
cmd/coord предоставляет общий CLI и приватный Unix API; Telepathy опционален.
Owner API требует отдельную capability. Git-проекция использует export intent
и cursor с явной политикой содержания.

См. SESSION_CLI.md для команд и границ доверия. Schema v1 не мигрируется автоматически.
Восстанавливается рабочий контекст, не скрытая история модели. Автозапуск ОС,
supervisor внешних writers, disaster restore из Git и автоматическая GitLab-синхронизация
не заявляются реализованными.
