# ADR-0002: Project Dependency Graph

- **Статус:** Accepted
- **Дата:** 2026-10-07
- **Редакционная пометка:** 2026-10-10: уточнены допустимые пары типов, EdgeID identity, семантика удаления, порядок replay/revision, терминология OWNER/Discussion Graph, DG-07 разбит на 07a–07e, API помечен как целевой, добавлен маркер OWNER decision для DG-08 cross-Task scope — FD, без изменения принятых инвариантов
- **Область:** зависимости и структура проекта в Coord и Dashboard
- **Связанные решения:** ADR-0001 Canonical Coordination Model; ADR-0003 External Reference Model; TASK-MODEL

## Контекст

Project Map должен показывать зависимости между задачами, milestones и ADR,
помогать понимать блокировки и видеть, что разблокируется после завершения
работы. Это отдельный граф проекта. Его нельзя смешивать с:

- Task Workflow — последовательностью этапов выполнения Task;
- Discussion Graph — фактами и решениями внутри одной Task.

Граф не должен становиться второй моделью Task или собственной логикой Dashboard.
Coord остаётся единственным владельцем канонических отношений проекта, а карта
является read-only проекцией.

## Решение

Ввести в каноническую модель Coord отношения проекта между типизированными
ссылками на узлы. Отношения и изменения отношений принадлежат Coord и
сохраняются как доменные факты. Dashboard строит из них Project Map.

### Узлы

```go
type GraphNodeRef struct {
    Kind NodeKind
    ID   string
}
```

В MVP допустимы узлы `TASK`, `ADR` и `MILESTONE`. Позже могут быть добавлены
`EPIC` и `RELEASE` отдельным расширением схемы.

`TASK` ссылается на канонический Task Coord; его `ID` — `TaskID` в формате
`task_<ULID>` по ADR-0003. Issue numbers, ticket keys и другие внешние
идентификаторы не являются ID TASK-узла и отклоняются по DG-01. `ADR` и `MILESTONE` являются
типизированными ссылками на документы или записи проекта; Graph хранит их
идентичность и связи, но не становится копией их содержимого. Формат внешней
ссылки и правила проверки её существования фиксируются в API/integration design.
Реестр и источник истины для ADR/MILESTONE этим ADR не выбираются. До их
определения операции, требующие проверки таких узлов, закрыты fail-closed;
реализация MVP может включать только TASK узлы, если у неё нет доверенного
каталога документов и milestones.

### Рёбра

```go
type GraphEdge struct {
    ID   string
    From GraphNodeRef
    To   GraphNodeRef
    Type EdgeType
}
```

Типы MVP:

- `DEPENDS_ON` — направленная зависимость;
- `RELATES_TO` — связь без утверждения о порядке или блокировке;
- `SUPERSEDES` — новый узел заменяет прежний;
- `CHILD_OF` — узел входит в родительский узел.

Каноническое направление зависимости:

```text
dependent              ──DEPENDS_ON──► prerequisite
TASK:task_<ULID-B>     ──DEPENDS_ON──► TASK:task_<ULID-A>
```

Для roadmap UI направление может быть обращено для чтения потока разблокировки:

```text
TASK:task_<ULID-A> ──blocks / unlocks──► TASK:task_<ULID-B>
```

`<ULID-A>`, `<ULID-B>` и т.п. в примерах — заполнители канонического ULID, а
не допустимые значения.

`BLOCKS` и `UNBLOCKS` — вычисляемые подписи/проекции; как отдельные рёбра они
не сохраняются. Для каждой упорядоченной пары `(dependent, prerequisite)` хранится
не более одного канонического `DEPENDS_ON`.

`EdgeID` является устойчивым уникальным идентификатором ребра, генерируемым Coord
при создании. Повтор команды добавления того же ребра с тем же idempotency key
ДОЛЖЕН возвращать существующий EdgeID, а не создавать новый. `EdgeID` не
определяется командой; знание пары `(From, To, Type)` не подразумевает знания
`EdgeID` до первого commit.

### Допустимые пары типов узлов и рёбер (активная MVP-схема)

До появления доверенного каталога ADR/MILESTONE активная MVP-схема разрешает
только ребра с обоими концами типа `TASK`. Все остальные пары отклоняются
fail-closed независимо от типа ребра.

| Edge type     | Допустимые пары узлов (MVP) |
|---------------|------------------------------|
| `DEPENDS_ON`  | `TASK → TASK`               |
| `RELATES_TO`  | `TASK → TASK`               |
| `SUPERSEDES`  | `TASK → TASK`               |
| `CHILD_OF`    | `TASK → TASK`               |

После определения доверенного resolver пары с `ADR` и `MILESTONE` вводятся
отдельным расширением схемы с явным решением OWNER.

### Целостность и изменения

Coord проверяет следующие инварианты:

- **DG-01 — существование ссылок.** Оба конца ребра разрешаются в узлы
  соответствующих типов. ADR/MILESTONE допустимы только после определения
  доверенного каталога и проверки существования; неизвестная ссылка
  отклоняется.
  Проверка: не реализовано
- **DG-02 — отсутствие циклов.** `DEPENDS_ON` не может образовать цикл.
  `CHILD_OF` также не может образовать цикл в иерархии.
  Проверка: не реализовано
- **DG-03 — типовая допустимость.** Пары типов узлов и рёбер проверяются по
  активной MVP-схеме (см. таблицу выше). `RELATES_TO` не означает dependency;
  `SUPERSEDES` имеет направление от нового узла к заменяемому. Все пары вне
  MVP-схемы отклоняются fail-closed.
  Проверка: не реализовано
- **DG-04 — идемпотентность.** Повторная команда добавления того же ребра с тем
  же idempotency key возвращает существующий EdgeID без создания дубликата. Повтор
  удаления того же ребра с тем же message ID возвращает прежний receipt. Новая
  команда удаления уже отсутствующего ребра возвращает структурированный
  `EDGE_NOT_FOUND` без изменения GraphRevision.
  Проверка: не реализовано
- **DG-05 — аудит изменений.** Добавление и удаление ребра записываются
  доменными событиями, например `PROJECT_EDGE_ADDED` и `PROJECT_EDGE_REMOVED`.
  Проверка: не реализовано
- **DG-06 — атомарность.** Изменение канонического графа и соответствующее
  DomainEvent фиксируются одной durable transaction. Если операция создаёт
  внешнее уведомление, Outbox входит в ту же транзакцию.
  Проверка: не реализовано
- **DG-06a — Graph Revision и порядок обработки команды.** Канонический Project
  Graph имеет монотонную `GraphRevision`. Порядок обработки команды изменения:
  авторизация → проверка субъекта/scope → проверка identity объектов (EdgeID,
  узлы) → replay lookup по idempotency key → сверка expected GraphRevision →
  проверка инвариантов → один durable commit. Replay lookup стоит до сверки
  GraphRevision: повтор уже принятой команды с исходной GraphRevision ДОЛЖЕН
  возвращать прежний receipt, а не конфликт. Конфликт GraphRevision применяется
  только к новой команде. Каждая успешная команда увеличивает GraphRevision в
  той же транзакции с ребром и событиями.
  Проверка: не реализовано

- **DG-07a — Eligibility первого Executor Run.** `TASK DEPENDS_ON TASK`-зависимость
  считается выполненной только когда prerequisite имеет `Status=COMPLETED`. Создание
  первого Executor Run допустимо лишь если выполнены все `DEPENDS_ON`; Coord
  проверяет это в той же транзакции, что и создание Run и передачу ownership. Пока
  зависимость не выполнена, dependent до первого старта остаётся `PENDING`.
  Проверка: не реализовано

- **DG-07b — Eligibility rework Run.** При rework (повторное создание Executor Run)
  применяется та же проверка: все `DEPENDS_ON` должны быть `COMPLETED`. При не
  выполненной зависимости Task остаётся `BLOCKED / EXECUTION` без нового writer Run.
  `COMPLETED` терминален, поэтому выполненная зависимость не может стать
  невыполненной между проверкой и commit.
  Проверка: не реализовано

- **DG-07c — Позднее добавление ребра.** Если `DEPENDS_ON` добавлено после того,
  как Task покинул `PENDING`, текущий Run не останавливается ретроактивно. Новый
  `DEPENDS_ON` для dependent, уже покинувшего `PENDING`, допускается только явной
  OWNER-командой. Последующее создание нового Executor Run проходит ту же
  проверку. Проекция показывает нарушенный порядок как Attention. `RELATES_TO`,
  `SUPERSEDES` и `CHILD_OF` на старт не влияют.
  Проверка: не реализовано

- **DG-07d — FAILED prerequisite.** Prerequisite в `FAILED` не разрешает старт и
  не завершает dependent автоматически. OWNER разрешает эту блокировку только
  явной Task-scoped командой, привязанной к `Task Revision` и `Graph Revision`:
  удалить конкретное ребро либо атомарно заменить его другим prerequisite. Решение
  и все изменения графа фиксируются в одном commit с `OWNER_DECISION` и
  соответствующими `PROJECT_EDGE_REMOVED`/`PROJECT_EDGE_ADDED` событиями. OWNER
  не может этой командой пометить prerequisite выполненным, обойти другие hard
  policy или назначить Run при оставшемся невыполненном prerequisite. Если после
  решения другие prerequisites ещё не `COMPLETED`, старт остаётся закрыт.
  Вычисленная проекция `blocks` и Attention для OWNER называют prerequisite и его Status.
  Проверка: не реализовано

- **DG-07e — Atomic edge replacement.** Замена ребра никогда не выполняется двумя
  отдельными commit и не открывает промежуточное состояние без зависимости. Атомарная
  замена входит в один durable commit. Зависимости на `ADR`/`MILESTONE` в MVP закрыты
  по DG-01: если такое ребро обнаружено в загруженном canonical state, readiness
  блокируется fail-closed.
  Проверка: не реализовано

- **DG-08 — авторизация команд графа.** Добавлять, удалять и заменять отношения
  может только OWNER через Task-scoped capability и с ожидаемой актуальной
  `GraphRevision`. Coord проверяет субъект, область capability, версии и все
  инварианты графа в одной command boundary. ORCHESTRATOR и агенты могут
  предложить изменение как Discussion/OWNER Attention, но не менять канонический
  граф напрямую. Создание Task вместе с начальными отношениями также требует
  OWNER authorization и атомарного commit.
  **Открытый вопрос перед реализацией (требует решения OWNER):** текущая
  формулировка «Task-scoped capability» не определяет, какой именно Task scope
  используется для ребра между двумя разными Tasks. Варианты: (A) capability
  scoped to dependent Task + expected GraphRevision; (B) отдельная
  ProjectGraph-scoped OWNER capability. Вариант A и B дают разные права OWNER;
  координатор не выбирает между ними самостоятельно. Решение требуется до начала
  реализации command boundary DG-08.
  Проверка: не реализовано

Graph Edge является каноническим фактом Coord. Dashboard не изменяет его и не
вычисляет новый roadmap из названий задач, текста обсуждений или порядка
отображения. Изменения выполняются через авторизованные команды Coord; их
конкретный CLI/write API определяется отдельно. Read-only Dashboard получает
только проекции.

## API

> **Примечание:** следующие endpoints являются целевым направлением API и не
> являются текущей product capability до принятия ADR-0006 и реализации
> read-only API.

Project Map отделён от Task Discussion Graph:

```text
GET /api/roadmap
GET /api/tasks/{id}/dependencies
```

`GET /api/roadmap` возвращает узлы и канонические рёбра. Ответ может содержать
проекционные поля вроде вычисленного `blocks`, но они не становятся
самостоятельным состоянием.

`GET /api/tasks/{id}/dependencies` возвращает зависимости и обратную проекцию:

```json
{
  "depends_on": ["task_<ULID-A>", "task_<ULID-C>"],
  "blocks": ["task_<ULID-D>", "task_<ULID-E>"]
}
```

Элементы — канонические `TaskID` по ADR-0003. `blocks` — обратная проекция
DEPENDS_ON; невыполненность зависимости (DG-07) показывается вместе со Status
prerequisite, а не выводится из факта наличия ребра.

Этот endpoint не заменяет `GET /api/tasks/{id}/graph`, который остаётся
Discussion Graph конкретной задачи.

## Представления Dashboard

- **Workflow View** — как Task проходит этапы `EXECUTION`, `REVIEW`, `AUDIT` и
  другие предусмотренные Stage Plan состояния.
- **Discussion Graph** — какие факты, находки и решения привели к действиям и
  результатам внутри Task. (UI-термин «Conversation Graph» является проекцией
  canonical Discussion Graph, а не отдельным графом.)
- **Project Map** — как Tasks, ADR и milestones связаны зависимостями,
  иерархией и отношениями замещения.

Все три представления читают канонические данные Coord. Они не вводят
собственных FSM, статусов или изменяемых копий отношений.

## Последствия

- Project Dependency Graph и Conversation Graph имеют разные узлы, смысл и
  endpoints.
- Зависимости становятся проверяемыми данными, а не только ссылками в тексте
  roadmap или внешней HTML-карте.
- Направление `DEPENDS_ON` однозначно; отображение блокировок строится его
  обратной проекцией.
- Сохранение и аудит отношений увеличивают доменную схему Coord и требуют
  версионирования, миграций и сценарных тестов на циклы, конфликтные изменения,
  идемпотентность и durable commit.
- Импорт текущих GitHub-зависимостей и сопоставление GitHub issue ↔ TaskID не
  подразумеваются этим ADR. Они требуют отдельного явного mapping и проверки
  источника данных.
- Каталог ADR/MILESTONE и его resolver являются предварительным условием для
  этих типов узлов; до их проектирования безопасен TASK-only Project Map.

## Критерии соответствия

Реализация соответствует ADR, если:

- Task Workflow, Conversation Graph и Project Dependency Graph остаются тремя
  отдельными представлениями;
- каноническая зависимость хранится как `dependent DEPENDS_ON prerequisite`;
- `BLOCKS` вычисляется из `DEPENDS_ON` и не хранится второй раз;
- без доверенного каталога ADR/MILESTONE Project Map MVP содержит только TASK
  узлы, а операции с другими типами узлов закрыты fail-closed;
- Coord отвергает несуществующие ссылки и циклы `DEPENDS_ON`/`CHILD_OF`;
- изменение ребра и его DomainEvent сохраняются атомарно;
- команда графа проверяет и увеличивает Graph Revision атомарно с изменением;
- TASK-узлы идентифицируются только `TaskID` по ADR-0003;
- dependent не покидает `PENDING`, пока хотя бы один его TASK-prerequisite не
  `COMPLETED`; каждый новый Executor Run, включая rework, проверяет все
  prerequisites; OWNER снимает FAILED prerequisite только атомарной
  авторизованной командой изменения графа и OWNER_DECISION (DG-07d/DG-08);
- Dashboard читает `/api/roadmap` и не изменяет граф;
- Discussion Graph endpoint не используется как Project Map и наоборот.
